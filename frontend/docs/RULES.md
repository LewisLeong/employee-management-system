# Frontend Rules

## 1. Purpose

This document defines the development rules for the Next.js frontend app.

The frontend must follow:

```text
FRONTEND_PRD.md
UI_SPEC.md
CODE_STYLE.md
```

---

## 2. Dependency Rule

Do **not** install any additional dependencies or third-party packages unless explicitly approved.

The frontend must be built using only the base dependencies that come with the selected Next.js setup.

Allowed base dependencies:

- Next.js
- React
- React DOM
- TypeScript, if selected during setup
- Default linting/config files generated by the framework setup

Do not install extra packages for:

- UI components
- Styling
- Tables
- Modals
- Forms
- Validation
- State management
- Icons
- Toast notifications
- Date formatting
- Utility helpers
- API clients

---

## 3. Styling Rule

Use only the styling method already included in the base Next.js setup.

Allowed:

- Plain CSS
- CSS Modules
- Global CSS
- Inline styles, only when simple and reasonable

Do not install styling libraries such as:

- Tailwind CSS, unless it was already selected during initial project setup
- Bootstrap
- Material UI
- Ant Design
- Chakra UI
- Mantine
- Styled Components
- Emotion
- Sass

---

## 4. UI Component Rule

All UI components must be built manually.

This includes:

- Table
- Modal
- Text input
- Switch
- Button
- Status badge
- Loading state
- Empty state
- Error message

Do not install component libraries.

---

## 5. Table Rule

The employee table must be implemented manually using native HTML table elements or custom React components.

Do not install table libraries such as:

- TanStack Table
- React Table
- AG Grid
- DataTables
- Material React Table

The table must support up to 1,000 employee records.

---

## 6. Modal Rule

The update modal must be implemented manually using React state and standard HTML/CSS.

Do not install modal libraries.

The modal must include:

- Name input
- Email input
- Active status switch
- Save button
- Cancel button

---

## 7. Form Rule

Form state must be implemented manually using React state.

Allowed:

```text
useState
useEffect
```

Do not install form libraries such as:

- React Hook Form
- Formik
- Final Form

---

## 8. Validation Rule

Frontend validation must be implemented manually.

Required validation:

| Field | Rule |
|---|---|
| name | Required |
| email | Required |
| email | Valid email format |
| isActive | Boolean |

Do not install validation libraries such as:

- Yup
- Zod
- Joi
- Valibot

---

## 9. State Management Rule

Use built-in React state.

Allowed:

```text
useState
useEffect
useMemo
useCallback
```

Do not install state management libraries such as:

- Redux
- Zustand
- Jotai
- Recoil
- MobX

---

## 10. API Rule

API request logic should be separated from UI components.

Recommended file:

```text
lib/api/employees.ts
```

The frontend must call:

```text
GET /employees
PATCH /employees/{id}
```

Use environment variable for API base URL:

```env
NEXT_PUBLIC_API_BASE_URL=http://localhost:8000/api
```

Do not hardcode API URLs directly inside components.

---

## 11. Frontend Scope Rule

Only implement the frontend features required by `FRONTEND_PRD.md`.

Required features:

- Employee list page
- Employee table
- Status display
- Update button for active employees only
- Update modal
- Save update API call
- Cancel modal action
- Loading state
- Error state
- Empty state
- Basic frontend validation

Do not add unrelated features unless requested.

Do not add:

- Employee creation UI
- Employee deletion UI
- Login page
- Role-based UI
- Dashboard charts
- Export features
- Advanced filters
- External themes

unless explicitly requested.

---

## 12. Component Structure Rule

Recommended structure:

```text
app/
  employees/
    page.tsx

components/
  employees/
    EmployeeTable.tsx
    EmployeeUpdateModal.tsx
    EmployeeStatusBadge.tsx
    EmployeeActions.tsx

lib/
  api/
    employees.ts

types/
  employee.ts
```

Each component should have one clear responsibility.

---

## 13. TypeScript Rule

Use clear types.

Recommended employee type:

```ts
export type Employee = {
  id: number;
  name: string;
  email: string;
  isActive: boolean;
};
```

Avoid using `any`.

Use proper types for:

- Employee data
- API payloads
- Component props
- Modal state
- Error state

---

## 14. UI/UX Rule

The UI should be clean, simple, and professional.

Prioritize:

- Readability
- Clear actions
- Good spacing
- Simple form flow
- Clear status display
- Clear loading states
- Clear error states

Do not copy the illustration exactly.

The illustration is only a functional reference.

---

## 15. Performance Rule

The employee table should support up to 1,000 records.

Because no extra dependencies are allowed:

- Use stable keys, such as `employee.id`
- Avoid unnecessary re-renders
- Avoid expensive calculations during render
- Keep rendering logic simple
- Use basic manual pagination only if needed

Do not install virtualization or pagination libraries.

---

## 16. Error Handling Rule

The app must handle:

- Employee list loading error
- Employee update error
- Validation error
- Empty employee list
- Employee not found response

Do not ignore API errors.

Do not silently fail.

---

## 17. Git Rule

Do not commit:

- `.env`
- `.env.local`
- `node_modules/`
- `.next/`
- `out/`
- `build/`
- Log files
- Temporary files

Frontend `.gitignore` should ignore:

```gitignore
node_modules/
.next/
out/
build/
.env
.env.*
!.env.example
*.log
.DS_Store
Thumbs.db
.vscode/
.idea/
```

---

## 18. Final Frontend Rule

When choosing between adding a dependency and writing simple custom React code, always write simple custom React code.

Dependencies are not allowed unless the project owner explicitly approves them.
